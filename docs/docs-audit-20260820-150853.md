This is the single current-status document for the audit. It describes the maintained `docs/` tree and current repository state; `new-docs` remains out of scope. Superseded observations and already-corrected factual defects are not kept as open findings.

## Current summary

The main GUI and command-line workflows are usable from the documentation: selecting a video, choosing background subtraction or YOLO, converting, entering tracking view, and exporting CSV/NPZ all worked. Output prefixes, compatible partial-conversion continuation, inclusive conversion ranges, current detector choices/defaults, and output filenames are now described according to current behavior.

The highest-priority open behavior questions are narrower:

1. The parameter-RST generator currently serializes some invocation/build-specific values as defaults.
2. The packaged macOS app has incomplete bundle metadata.
3. The documented `pvconvert` utility is absent from the audited package.
4. Some headless success paths emit misleading progress or error-like shutdown diagnostics.

## What works directly from the documentation

- A Conda environment created from the local build channel plus conda-forge resolves the package and its dependencies. The environment must be activated, as the installation documentation says.
- The welcome screen, video selection, Locations/Detection/Tracking configuration, conversion, tracking view, and export workflow are present and usable.
- Both `background_subtraction` and `yolo` conversion work. The documentation now also names `precomputed`, `sam3`, and `none` rather than claiming only two detection modes exist.
- The documented YOLO defaults now match the configuration UI: confidence `0.1`, IoU `0.5`, and model `yolo26n.pt`.
- With no output directory or prefix, conversion writes beside the selected input. A hardlink with a different basename receives its own neighboring `.pv` and associated files.
- `output_prefix` moves every output, including the PV, below the prefix directory.
- A compatible partial PV resumes from the next source frame. Intentional replacement is a separate start-over operation.
- Conversion ranges have inclusive endpoints. `[4,7]` means frames `4`, `5`, `6`, and `7`.
- CSV and NPZ exports are readable with the Conda-resolved NumPy. Exported filenames use `individual_prefix`, whose current default is `id`.
- CSV has one leading structural `frame` column. `frame` is no longer selectable in the export GUI, and manually listing it does not create a duplicate CSV column. Equivalent output-field instances are treated as an ordered set; NPZ retains one configured `frame` array.
- Calibration is documented. `tutorials.rst` already explains the **Calibrate** button, choosing two points, entering the real-world distance, and applying the resulting `cm_per_pixel`; `gui.rst` and `run.rst` also cover it. The quick-start sequence now points users to calibration explicitly.

## Current documentation structure

The obsolete `trexa.rst`, `UsageTracker.md`, and `commons_gui.rst` pages are deleted. The maintained navigation contains installation, quick start, tutorials, model training, running, updates, examples, GUI, batch processing, formats, generated parameters, and FAQ pages.

Project artifacts are now described by role rather than introduced incidentally:

- `.pv` is the preprocessed detection/video cache.
- `.settings` is per-video configuration.
- `.results` is reloadable TRex analysis state. When conversion continues directly into tracking, it can be created and populated before a manual trajectory export; it is not the primary trajectory interchange format.
- CSV/NPZ files below the data output location are exported analysis data.

The base/default-versus-recommended-value distinction is explicit in the tutorial and in the owning `track_threshold` description in `Application/src/tracker/core/default_config.cpp`. The compiled base is `0`; initializing a background-subtraction configuration applies the task-specific suggested value `15`. An explicit user value wins. The regenerated `parameters_trex.rst` now contains the same explanation.

The parameter reference was regenerated on 2026-08-21. The authoritative corrections for inclusive `video_conversion_range`, output-field set semantics, and the base/task-specific `track_threshold` values all survived regeneration because their prose is owned by the two `default_config.cpp` files. Regeneration also removed parameters no longer registered, added newly registered parameters, updated current types such as `optional<float>` for `detect_iou_threshold`, and corrected the `meta_encoding` value descriptions from the enum documentation.

The regeneration also exposed two current generator facts:

- Some low-level keypoint and tiled-detection prose had previously been edited directly in the generated RST and therefore did not survive regeneration. It was not restored: parameter explanations must be written for users in the owning `default_config.cpp`, not preserved as internal implementation notes in generated documentation.

The current code makes `pvinfo` treat explicitly requested reports as output even in quiet mode. This applies to `blob_detail` and the OpenCV FFmpeg/OpenCL support reports; routine initialization and progress remain quiet. `run.rst` demonstrates `pvinfo -blob_detail -quiet` again. ## Behavior that still requires source inspection

These facts are not yet discoverable enough from the user documentation alone:

- Settings come from multiple layers: compiled defaults, detector/task-specific suggested defaults, command line, PV metadata, per-video `.settings`, and GUI/source-map overrides. The exact exclusion and precedence rules currently require reading `SettingsInitializer.cpp`.
- NPZ archives contain both per-frame series and differently shaped metadata/tracklet arrays. The Positional Data section still reads too much like every NPZ member is a same-length per-frame metric.
- First-use YOLO model resolution/download behavior is not documented well enough for an offline or freshly installed environment.
- Several background-subtraction decisions—especially the relationship among `num_pixels`, `cm_per_pixel`, size filters, history splitting, speed constraints, and the `noise` label—still require source knowledge or experimentation.
- The exact set of settings that are intentionally forbidden in reusable files versus accepted only from the command line is not presented as one coherent table.

## Settings loading and access semantics

A real-file settings matrix has been added to `test_tracking_filename_resolution.cpp`:

| Source/rule | Settings exercised | Required result |
|---|---|---|
| Ordinary per-video values | `track_threshold`, `auto_quit` | Loaded from the file |
| `default_excludes` | `nowindow`, `gui_interface_scale`, `load`, `task`, `filename`, `source` | Ignored by settings sources governed by this base exclusion list |
| STARTUP/SYSTEM access | `nowindow`, `python_path`, `gui_interface_scale`, `app_name` | Ignored |
| Invocation-owned paths | `output_dir`, `output_prefix` | The initial command-line-derived source map supplies them; a later load may supply new paths after ordinary command-line state is consumed |
| External model fields, no manual model | `detect_model`, `region_model`, both resolutions | Model paths load; SYSTEM resolutions do not |
| External model fields, manual model | all four model/resolution fields | Current manual model wins and the remaining external model fields are ignored |
| Unconditional external exclusions | `video_conversion_range`, `settings_file`, `output_dir`, `filename`, `source` | Ignored when loading reusable `.settings` and PV-provided settings |
| Initial command-line values | integer, floating-point, string, Boolean, and byte-valued settings | The command-line-derived source map survives task defaults and `.settings` during the initial load |
| Caller exclusion | `individual_prefix`, `track_threshold` | The excluded field remains at its default while an unrelated allowed source-map field still loads |
| Later GUI/source-map load | paths, `track_threshold`, `individual_prefix` | Explicit values replace ordinary command-line values after the initial load has consumed them |

The test mirrors the three production list categories—default exclusions, model-conditional exclusions, and unconditional external exclusions—and then compares its expected names with the production arrays. Adding or removing a production entry therefore forces the typed behavior matrix to be reviewed. No production settings-loading changes were made as part of this audit update.

Application-level regression cases have also been added to `test-headless-convert-exit`. They launch the real executable to distinguish command-line precedence, ordinary `.settings` loading, and registered defaults. A four-layout matrix then launches the same video twice without forcing a task: the first invocation must create the missing PV, while the second must leave that PV byte-for-byte unchanged and recreate tracking results and CSV exports. These cases are pending the user-run build and test described below.

Explicit output filenames now have one boundary across the settings loader and output-name resolver. A relative value is a basename: GUI entry visibly normalizes away directory components, while a headless invocation with relative directory components terminates with an exception before creating output. An absolute filename is authoritative, clears `output_prefix`, and places all associated output relative to its absolute parent. The owning `filename` parameter description and regenerated parameter RST contain this rule.

The declared access levels are not generally ignored. `GlobalSettings::load_from_string` and `load_from_file` reject values above the caller's access ceiling; `SettingsInitializer` additionally turns SYSTEM and later STARTUP settings into explicit exclusions at the appropriate stages. The settings GUI, web settings endpoint, Python setting writer, config serialization, and reset paths also consult access levels.

They are not a universal permission boundary, however. Direct C++ writes through `SETTING(...)` are unrestricted by design, and several low-level `sprite::parse_values` calls used for PV/result metadata do not inspect access levels themselves. Those paths are safe only when their caller supplies the correct exclusion set or parses into a limited local map. Access levels should therefore be understood as loader/UI policy metadata, not as security capabilities enforced by the property object everywhere.

## Open program and package issues

### macOS application metadata

`Application/src/tracker/AlterInfo.plist` currently omits `CFBundleIdentifier`, `CFBundleName`, `CFBundleExecutable`, `CFBundlePackageType`, and `CFBundleInfoDictionaryVersion`. The main target does set CMake bundle properties, but a custom plist template must contain the corresponding substitutions for them to appear in the final bundle. The target also overrides the project-wide `com.trexing.trex` identifier with the less stable-looking `app.trex.run.a`.

The plist should contain at least:

```xml
<key>CFBundleName</key>
<string>${MACOSX_BUNDLE_BUNDLE_NAME}</string>
<key>CFBundleDisplayName</key>
<string>${MACOSX_BUNDLE_BUNDLE_NAME}</string>
<key>CFBundleExecutable</key>
<string>${MACOSX_BUNDLE_EXECUTABLE_NAME}</string>
<key>CFBundleIdentifier</key>
<string>${MACOSX_BUNDLE_GUI_IDENTIFIER}</string>
<key>CFBundleInfoDictionaryVersion</key>
<string>6.0</string>
<key>CFBundlePackageType</key>
<string>APPL</string>
```

The main target should use one stable reverse-DNS identifier, for example the existing project value `com.trexing.trex`, a bundle name/display name of `TRex`, and the generated executable name `TRex`. The prototype target needs its own identifier and display name even if it shares a template.

This is useful beyond audit automation. Complete, stable metadata improves Launch Services registration, Finder naming, `open -a` behavior, `.pv` document association, accessibility/automation targeting, stable camera/privacy permission identity, crash-log attribution, and future code-signing/notarization behavior.

### Other open runtime/package findings

- `pvconvert` is described as part of the standard installation in `examples.rst`, and the Conda recipe references it, but it is absent from the audited package. Either package the executable and add a manifest smoke test, or replace/remove the example.
- A successful bounded headless YOLO run returned status 0 and produced consistent outputs, but emitted cancellation/unregistered-pipeline/open-promise/out-of-range-frame diagnostics during shutdown. Successful batch output should not resemble a partial failure.
- After an 11-frame bounded conversion, tracking progress was labelled `Converting .../240`; the phase name and denominator were misleading even though the artifacts were valid.
- The Conda post-link process consults or updates the user-global Ultralytics settings file under `~/Library/Application Support/Ultralytics`. The exact before/after mutation has not yet been isolated.

Repository policy now requires documentation-derived executable behavior, confirmed issues, and newly documented boundary principles to be backed by the smallest adequate regression test. It also requires closing keywords only when a commit fully resolves the linked GitHub issue.
User-facing documentation must not contain bug reports, temporary workarounds, or implementation-status notes: unresolved bugs belong in GitHub issues, while requested fixes require code plus focused regression coverage before supported behavior is documented.
